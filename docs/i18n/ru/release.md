Выпуски запускаются вручную. Не публикуйте их из процессов pull request.

> [!IMPORTANT]
> Запускайте выпуски из `main`, сохраняйте одинаковые значения в `VERSION` и
> параметре процесса, а также явно решайте, требует ли выпуск повышения
> минимальной версии CLI.

<a id="release-at-a-glance"></a>
## Краткая схема выпуска

| Этап | Результат |
| --- | --- |
| Подготовить и объединить изменение версии | Источники версии в репозитории согласованы |
| Запустить Package Preview | Артефакты в формате выпуска собраны без публикации |
| Проверить предварительные артефакты | Проверены архивы, манифест, хеши и структура CEF для Linux |
| Запустить Release из `main` | Опубликованы тег и выпуск GitHub |
| Выполнить дымовую проверку установки и обновления | Проверен общедоступный пользовательский процесс |

<a id="versioning"></a>
## Управление версиями

`VERSION` является источником истины.

Средства выпуска принимают значения SemVer. Стабильные выпуски используют
`X.Y.Z`. Тестовые кандидаты используют изолированную предварительную версию
pull request, например `1.2.3-pr.101.2`, где `pr-101` является тестовым каналом,
а `2` обозначает номер кандидата в этом канале.

Чтобы изменить версию репозитория:

```bash
node scripts/set-version.mjs X.Y.Z
```

Сценарий обновляет:

- `VERSION`
- `godot_demo/addons/fennara/VERSION`
- константы версии плагина
- версию пакета рабочего пространства Rust в `local/`
- `local/Cargo.lock`

Дополнение также содержит `addons/fennara/release.json`. При выполнении обычной
команды выше стабильный идентификатор записывается автоматически. Для рабочей
области тестовой сборки используются явные параметры идентификатора:

```bash
node scripts/set-version.mjs 1.2.3-pr.101.2 \
  --track staging \
  --channel pr-101 \
  --source-commit <full-commit-sha>
```

Тестовая версия, канал, исходный коммит и точный тег выпуска должны совпадать.
Дополнение предварительного выпуска без такого идентификатора отклоняется.
Существующие стабильные дополнения, выпущенные до появления `release.json`,
по-прежнему по умолчанию относятся к стабильному каналу.

Проверьте синхронизацию версий:

```bash
node scripts/check-version.mjs
```

<a id="1-prepare-the-release-commit"></a>
## 1. Подготовьте коммит выпуска

1. Запустите сценарий изменения версии.
2. Проверьте разницу.
3. Выполните локальные проверки, соответствующие измененной области.
4. Объедините PR подготовки выпуска в `main`.

Обычные проверки:

```bash
node scripts/check-version.mjs
cd local
cargo test --locked
```

Если менялась GDExtension, по возможности также соберите дополнение локально:

```bash
cd fennara-cpp
scons platform=windows target=editor
```

<a id="2-run-package-preview"></a>
## 2. Запустите Package Preview

Используйте этот процесс перед публикацией, если менялась упаковка или вам нужен
пробный запуск.

GitHub:

```text
Actions > Package Preview > Run workflow
```

Процесс собирает пакеты Windows, Linux и macOS и загружает временные артефакты.
Он не создает теги, выпуски GitHub или `latest`.

Package Preview достаточно точно повторяет непубликующие этапы Release, чтобы
проверить упаковку выпуска до объединения:

- синхронизирует не требующий сборки интерфейс чата и исходные вспомогательные
  файлы среды выполнения с данными дополнения;
- собирает ZIP-архив среды выполнения CEF для Linux;
- записывает сгенерированный манифест среды выполнения CEF для Linux;
- передает этот сгенерированный манифест сборкам пакетов для платформ;
- формирует архив дополнения для всех платформ;
- переименовывает локальные пакеты и пакеты дополнения в имена ресурсов выпуска,
  которыми управляет манифест;
- проверяет ресурс среды выполнения CEF для Linux по сгенерированному манифесту;
- записывает `fennara-release-manifest-v<version>.json`;
- загружает один артефакт `fennara-package-preview-release-assets`, содержащий
  ZIP-архивы в формате выпуска и манифест.

Предварительные артефакты полезны для проверки содержимого ZIP-архивов и формы
манифеста перед публикацией. Это артефакты Actions, а не общедоступные ресурсы
выпуска.

<a id="3-run-release"></a>
## 3. Запустите Release

Запустите ручной процесс выпуска из `main`:

```text
Actions > Release > Run workflow
```

Параметры:

```text
version: X.Y.Z
promote_latest: true
```

Параметр `version` должен совпадать с `VERSION`.

Процесс публикует:

- `v<version>`
- помечает `v<version>` как последний выпуск GitHub, если `promote_latest`
  имеет значение true.

Процесс выпуска подготавливает среду выполнения CEF для Linux до упаковки
платформ. Он скачивает закрепленный официальный минимальный SDK CEF 139 для
Linux, формирует отдельный архив
`fennara-webview-cef-linux-x64-<cef-version>.zip`, удаляет отладочные символы из
подготовленных двоичных файлов ELF, записывает сгенерированный включенный
манифест `local/webview-runtimes/linux-cef.json` и передает его в пакеты CLI.
Затем задача публикации проверяет, что среди ресурсов выпуска есть архив CEF с
точным именем из сгенерированного манифеста и что его SHA-256 совпадает. Она
также записывает `fennara-release-manifest-v<version>.json`, проверяет каждый
указанный ресурс и хеш и загружает манифест вместе с выпуском.

Процессы pull request не публикуют выпуски. Процесс Package Preview создает
тестовые артефакты в формате выпуска, включая манифест и данные среды выполнения
CEF для Linux, чтобы сопровождающие могли выполнить дымовую проверку упаковки
до объединения. Package Preview не является пользовательским каналом выпуска.

<a id="release-assets"></a>
## Ресурсы выпуска

Каждый выпуск должен содержать пакеты CLI и локальной среды выполнения для
каждой платформы и один общий пакет дополнения для всех платформ.

| Цель | Ресурсы |
| --- | --- |
| Windows x86_64 | `fennara-cli-windows-x86_64-v<version>.zip`<br>`fennara-release-local-windows-x86_64-v<version>.zip` |
| Linux x86_64 | `fennara-cli-linux-x86_64-v<version>.zip`<br>`fennara-release-local-linux-x86_64-v<version>.zip`<br>`fennara-webview-cef-linux-x64-<cef-version>.zip` |
| macOS arm64 | `fennara-cli-macos-arm64-v<version>.zip`<br>`fennara-release-local-macos-arm64-v<version>.zip` |
| Все платформы | `fennara-release-addon-v<version>.zip`<br>`fennara-addon-latest.zip`<br>`fennara-release-manifest-v<version>.json` |

Роли пакетов:

| Шаблон | Роль |
| --- | --- |
| `fennara-cli-*` | Данные сценария установки, содержащие только CLI `fennara` для одной платформы |
| `fennara-release-local-*` | Программы запуска MCP и фоновой службы, а также версионные двоичные файлы среды выполнения для одной платформы |
| `fennara-release-addon-v*` | Версионное дополнение для всех платформ, определяемое через манифест выпуска |
| `fennara-addon-latest.zip` | Псевдоним дополнения для всех платформ со стабильным именем, предназначенный для документации и ручного скачивания |
| `fennara-webview-cef-linux-x64-*` | Общая среда выполнения CEF только для Linux, один раз устанавливаемая в данные приложения Fennara |
| `fennara-release-manifest-v*` | План установки и обновления с именами ресурсов, значениями SHA-256, примитивами установки и общими средами выполнения |

GDExtension дополнения для macOS сейчас не нотарифицирована Apple. Загрузка
через браузер и ручная распаковка в Finder могут распространить метаданные
карантина и вызвать уведомление проверки macOS. Пользовательская документация
по установке должна рекомендовать `fennara install` в macOS, объяснять
ограничение ручного ZIP-архива и предлагать затронутым пользователям удалить
скопированное вручную дополнение перед повторной установкой через CLI. При
проверке выпуска простое создание ZIP-архива не считается подписанием или
нотарификацией в macOS.

Префикс `fennara-release-local-*` не позволяет старым версиям CLI незаметно
обходить путь пакета под управлением манифеста.

<a id="release-manifest"></a>
## Манифест выпуска

Начиная с версии 0.3.0, `fennara install` и `fennara update` предпочитают
манифест выпуска, если он опубликован в выпуске. Манифест содержит:

- `schema_version`
- `version`
- `minimum_cli_version`
- поддерживаемые примитивы установки
- ресурсы CLI и локальной среды выполнения для каждой платформы с хешами SHA-256
- общий ресурс дополнения с SHA-256
- зависящие от платформы ресурсы общих сред выполнения, сейчас это CEF для Linux

Файл `scripts/release-policy.mjs` является источником истины для
`minimum_cli_version`. Средство записи манифеста выбирает политику после
проверки идентификатора выпуска, поэтому Stable, Package Preview и Staging не
могут выбирать независимые значения. Обычные изменения структуры пакетов или
имен ресурсов должны описываться данными манифеста, а не изменениями внешнего
CLI. Повышайте значение политики, когда выпуску требуется более новая передача
управления средству обновления, схема манифеста, примитив установки, поведение
самостоятельного обновления или другая возможность CLI, которую старый
опубликованный CLI не может безопасно выполнить.

Если CLI слишком стар, `fennara update` должна сначала обновить установленный
CLI с помощью записи `assets.cli` для соответствующей платформы из манифеста, а
затем продолжить обновление пакета с `--no-self-update`. Если самостоятельное
обновление недоступно для этого выпуска или места установки, команда должна
завершиться до установки пакетов и вывести ясное указание повторно запустить
`install.sh` или `install.ps1`.

Необязательный идентификатор выпуска, добавленный в схему манифеста 1, не
требует повышения минимальной версии CLI. Старые клиенты схемы 1 игнорируют
неизвестные поля, а клиенты с поддержкой тестового канала проверяют идентификатор,
когда он присутствует. Для будущего выпуска, зависящего от активации с учетом
канала или передачи управления средству обновления, минимальную версию CLI
нужно пересмотреть до публикации.

<a id="staging-identity-and-discovery-contract"></a>
## Контракт идентификатора и обнаружения тестового канала

Тестовые каналы изолированы для каждого pull request:

| Значение | Пример для PR 101 |
| --- | --- |
| Канал | `pr-101` |
| Версия кандидата | `1.2.3-pr.101.2` |
| Точный выпуск | `v1.2.3-pr.101.2` |
| Ссылка канала | `fennara-staging/pr-101` |
| Файл указателя | `fennara-staging-channel-pr-101.json` |

Ссылка Git каждого канала содержит только небольшой файл-указатель на точный
версионный выпуск. Двоичные файлы выпуска никогда не находятся по перемещаемой
ссылке канала. CLI может разрешить этот указатель с помощью внутреннего запроса
версии `channel:pr-101`, после чего продолжает использовать только точную
версию.

Поэтому PR 101 и PR 125 используют разные теги выпуска и ресурсы указателя.
Обновление одного канала не может перенаправить тестировщиков другого канала.
Публикация одного канала никогда не меняет обозначение последнего стабильного
выпуска GitHub или канал другого pull request.

<a id="staging-candidate-workflow"></a>
## Процесс тестового кандидата

Ручной процесс **Staging Release** собирает кандидата из текущей вершины
открытого pull request. Запустите его из `main` и передайте:

| Параметр | Значение |
| --- | --- |
| `pull_request` | Открытый pull request для сборки |
| `base_version` | Планируемая стабильная версия в формате `X.Y.Z` |
| `candidate` | Возрастающий номер кандидата для этого pull request |
| `source_commit` | Необязательный полный SHA, который все еще должен быть вершиной pull request |
| `publish` | Выключено для проверки только артефактов, включено для публикации кандидата |

Процесс фиксирует SHA вершины pull request перед сборкой для любой платформы.
Задачи Windows, Linux и macOS извлекают именно этот коммит с разрешениями только
на чтение, без сохраненных учетных данных Git, без учетных данных выпуска и без
возможности сохранять общие кеши зависимостей. Они могут восстанавливать
совместимые кеши SCons/godot-cpp и Cargo, записанные доверенными процессами
ветви по умолчанию. Тестовая сборка использует действие только для
восстановления кеша, поэтому код кандидата может потреблять доверенные результаты
сборки, но не может заменить или отравить кеши для последующих запусков. Код
кандидата может создавать артефакты сборки, но не может публиковать выпуск
GitHub.

Затем доверенные сценарии репозитория проверяют идентификатор кандидата, точный
состав архивов, содержимое дополнения, структуру пакетов платформ, манифест
выпуска и каждое значение SHA-256. Публикация остается отключенной, пока
`publish` не будет выбран явно.

Когда публикация включена, доверенная финальная задача:

1. Повторно проверяет артефакты кандидата как данные.
2. Создает черновик, загружает каждый ресурс и публикует его как точный
   предварительный выпуск `v<exact-version>`, не изменяя последний выпуск GitHub.
3. Скачивает опубликованные ресурсы и сравнивает их имена и хеши.
4. Отклоняет обратное или конфликтующее изменение канала.
5. В последнюю очередь обновляет небольшую ссылку-указатель
   `fennara-staging/pr-<number>` через условную запись GitHub Contents API.
6. Скачивает активный указатель и проверяет его точное содержимое.

Запуски для одного pull request выполняются последовательно. Разные pull request
используют отдельные группы параллелизма, теги выпусков и ссылки-указатели.
Повторный запуск того же кандидата проверяет существующий точный выпуск, а не
смешивает с ним файлы. Процесс никогда не создает, не загружает данные в
стабильный последний выпуск GitHub и не назначает его.

Для стабильной публикации не используется буквальный тег или выпуск `latest`.
Процесс Release создает точный выпуск `v<version>` как черновик, побайтово
проверяет загруженные ресурсы, публикует его как изменяемый выпуск и помечает
именно этот выпуск как последний выпуск GitHub, если `promote_latest` имеет
значение true. Установщики и стабильное обнаружение CLI используют конечную
точку API последнего выпуска GitHub.

Пока неизменяемость выпусков репозитория отключена, стабильные и тестовые
выпуски остаются изменяемыми. Оба процесса проверяют метаданные выпуска и байты
скачанных ресурсов перед завершением публикации или продвижением тестового
канала. Для публикации ресурсов используется `GITHUB_TOKEN` конкретной задачи
с доступом на запись содержимого.

Политика выпуска сейчас требует CLI `0.4.1` для стабильных манифестов и CLI
`0.3.8` для тестовых манифестов. Стабильное обнаружение больше не использует
удаленный тег `latest`. Стабильной версии `0.4.1` нужны исправленная проверка
обновления, предварительная проверка переключения версий, обработка журнала
операций Windows и исправление маркера среды выполнения Linux CEF. Тестовый кандидат наподобие `0.4.1-pr.123.1` считается по
SemVer ниже стабильной версии `0.4.1`, поэтому его минимальная версия должна
оставаться ниже версии кандидата, чтобы при первоначальной настройке можно было
установить CLI кандидата. Не меняйте ни одно из минимальных значений только на
основании совместимости схемы манифеста.

Общий ZIP-архив дополнения содержит все собранные двоичные файлы GDExtension,
указанные в `godot_demo/addons/fennara/fennara.gdextension`. Godot загружает
библиотеку, соответствующую операционной системе пользователя, и игнорирует
остальные.

Данные веб-представления CEF для Linux находятся отдельно от архива дополнения.
При упаковке выпуска создается включенный манифест среды выполнения, а его
данные встраиваются в `fennara-release-manifest-v<version>.json`. CLI один раз
устанавливает соответствующие данные CEF в каталог данных приложения Fennara
пользователя:

```text
webview/cef/linux-x64/<cef-version>/
```

Не размещайте `libcef.so`, вспомогательные исполняемые файлы CEF, ресурсы CEF
или пакеты локалей внутри `fennara-addon-*`. Package Preview собирает отдельный
артефакт CEF для тестирования и записывает такой же сгенерированный манифест
среды выполнения, как Release, но единственным пользовательским источником
ресурсов выпуска остается публикация выпуска.

Для сборок GDExtension в Linux также нужен исходный код оболочки официального
SDK CEF, но файлы среды выполнения CEF в дополнение не входят. CI выполняет:

```bash
node scripts/prepare-linux-cef-sdk.mjs
```

и передает извлеченный каталог в SCons как `FENNARA_CEF_ROOT`. SCons использует
`FENNARA_CEF_ROOT/libcef_dll/` для сборки небольшой библиотеки дополнения
`libfennara_linux_cef_bridge.so` с закрепленной оболочкой C++ CEF 139. Загрузка
SDK проверяется по версии и хешу, поскольку сгенерированный исходный код
оболочки должен соответствовать ABI среды выполнения CEF. Мост упаковывается
вместе с дополнением, а `libcef.so`, ресурсы, пакеты локалей и
`fennara_cef_helper` остаются в отдельной общей среде выполнения CEF.

Сценарии упаковки завершаются с ошибкой, если файлы среды выполнения CEF
обнаружены внутри архива дополнения. Ресурс среды выполнения должен называться:

```text
fennara-webview-cef-linux-x64-<cef-version>.zip
```

ZIP-архив должен распаковывать обязательные файлы в своем корне:

```text
libcef.so
fennara_cef_helper
icudtl.dat
resources.pak
chrome_100_percent.pak
chrome_200_percent.pak
v8_context_snapshot.bin
locales/en-US.pak
```

Если они присутствуют в выбранном дистрибутиве CEF, следует также включить
необязательные файлы среды выполнения CEF: `chrome-sandbox`, `libEGL.so`,
`libGLESv2.so`, `libvk_swiftshader.so`, `libvulkan.so.1`,
`vk_swiftshader_icd.json`, `snapshot_blob.bin` и дополнительные
`locales/*.pak`.

Чтобы вручную сформировать архив среды выполнения из выбранного сопровождающим
дерева двоичных файлов CEF:

```bash
node scripts/prepare-linux-cef-runtime.mjs \
  --cef-root /path/to/cef_binary_<version>_linux64_minimal \
  --version <cef-version> \
  --out-dir dist/cef-runtime
```

В Linux сценарий собирает `fennara_cef_helper` из
`scripts/cef/linux/fennara_cef_helper.cpp` с официальными заголовочными файлами
CEF из `fennara-cpp/vendor/cef/`. В другой ОС сначала соберите этот
вспомогательный файл в Linux и передайте
`--helper /path/to/fennara_cef_helper`. Используйте `--dry-run`, чтобы
просмотреть выбранные файлы до записи ZIP-архива.

После того как сценарий выведет SHA-256, обновите
`local/webview-runtimes/linux-cef.json`:

```json
{
  "version": "<cef-version>",
  "enabled": true,
  "archive": {
    "format": "zip",
    "name": "fennara-webview-cef-linux-x64-<cef-version>.zip",
    "url": null,
    "sha256": "<sha256>"
  }
}
```

Для обычных выпусков процесс автоматически записывает манифест среды выполнения
CEF для Linux с `--write-manifest`, затем `scripts/write-release-manifest.mjs`
копирует поля среды выполнения в
`fennara-release-manifest-v<version>.json`. Не включайте вручную хранящийся в
репозитории заполнитель манифеста, если вы намеренно не отлаживаете путь к
ручному ресурсу среды выполнения или прежнее резервное поведение. Если
сгенерированные данные манифеста указывают на отсутствующий ресурс или его
SHA-256 не совпадает, процесс Release и команды Linux `fennara install` /
`fennara update` завершаются с понятной ошибкой.

CLI должен публиковать обновления среды выполнения CEF для Linux атомарно:
извлечь и проверить их в промежуточном каталоге, записать маркер среды выполнения
только после появления обязательных файлов, затем опубликовать каталог версии
и обновить `current.json` переименованием временного файла. Установленный маркер
`fennara-cef-runtime.json` должен определять контракт нативного загрузчика с
помощью `"runtime": "cef"`. Установка и обновление исправляют совпадающий старый
маркер, содержащий только `"kind": "cef"`, без повторного скачивания данных CEF.
Запущенные редакторы продолжают использовать уже загруженную среду выполнения.

CLI встраивает сгенерированные шаблоны инструкций проекта из `local/templates/`.
При сборке CLI для выпуска эти шаблоны компилируются в двоичный файл вместе с
остальным кодом CLI.

<a id="what-latest-means"></a>
## Что означает `latest`

Указатель последнего выпуска GitHub выбирает версионный выпуск, используемый
обычными процессами установки и обновления. Fennara не создает и не перемещает
буквальный тег `latest`.

- `install.ps1` и `install.sh` по умолчанию получают ресурс CLI последнего
  выпуска.
- `fennara update` по умолчанию получает манифест через конечную точку последнего
  выпуска GitHub, при необходимости самостоятельно обновляет установленный CLI,
  затем определяет по манифесту локальные ресурсы, дополнение и общие среды
  выполнения.
- Обновления в редакторе до завершения работы подготавливают проверенные ресурсы,
  повторно проверяют дайджест всего подготовленного дополнения перед заменой,
  сохраняют прежнее дополнение, программы запуска и манифест среды выполнения
  до успешной проверки активации и требуют рукопожатия вновь открытой
  GDExtension до удаления данных отката.
- `fennara install` по умолчанию получает манифест через конечную точку последнего
  выпуска GitHub, затем определяет по нему локальные ресурсы, дополнение и общие
  среды выполнения.
- Проверка обновлений плагина Godot сравнивает версию с последним выпуском GitHub.

Используйте `promote_latest: false` только при публикации версии, которая не
должна становиться стандартной пользовательской установкой.

Установщики и скачивание выпусков должны выводить метаданные выпуска, а также
этапы скачивания ресурсов, извлечения, установки и проверки. Сетевые запросы
должны использовать ограниченное время ожидания, чтобы зависание GitHub/CDN
завершалось диагностикой, а не выглядело как остановка. В Windows `install.ps1`
должен проверять код выхода CLI до вывода сообщения об успехе. Код выхода
`-1073741515` (`0xC0000135`) означает, что исполняемый файл CLI был записан, но
Windows не смогла запустить его из-за отсутствующей DLL. Сообщите пользователю,
что нужно установить Microsoft Visual C++ Redistributable 2015-2022 x64, а
затем повторно запустить `fennara --version`, `fennara doctor` и
`fennara install`. Адрес загрузки:
`https://aka.ms/vs/17/release/vc_redist.x64.exe`.

<a id="smoke-test-after-release"></a>
## Дымовая проверка после выпуска

В Windows:

```powershell
irm https://raw.githubusercontent.com/fennaraOfficial/fennara-godot-ai/main/install.ps1 | iex
fennara --version
fennara doctor
```

В проекте Godot:

```bash
cd path/to/your-godot-project
fennara install
fennara mcp-setup --claude
```

Убедитесь, что проект получил:

```text
AGENTS.md
addons/fennara/ai/
```

Откройте проект в Godot, затем попросите приложение MCP:

```text
Use Fennara MCP to run fennara_status and tell me which Godot project is connected.
```

Проверка обновления:

```bash
cd path/to/your-godot-project
fennara update
fennara self-update
```

<a id="rules"></a>
## Правила

- Процесс Release запускается только из `main`.
- Параметр версии Release должен совпадать с `VERSION`.
- Процессы pull request могут собирать и загружать тестовые артефакты, но не
  должны публиковать выпуски.
- Выпуск, предназначенный для обычных пользователей, должен быть назначен
  последним выпуском GitHub.
- Не перезаписывайте опубликованные теги выпусков, если сопровождающие не приняли
  намеренное решение заменить неисправный выпуск.
